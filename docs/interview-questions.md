## Python

### Q1. Why use `Protocol` instead of abstract base classes for provider interfaces?
- **Concise:** Protocols give structural typing: any class with the right methods satisfies the
  interface without inheriting from it, and mypy checks it statically.
- **Senior:** It decouples implementations from the interface module — the LangChain adapters,
  the mock and test fakes all satisfy `LLMProvider` (`app/providers/llm/base.py`) without
  importing a base class, which keeps heavy SDK imports optional. The trade-off is no runtime
  enforcement unless you add `@runtime_checkable`, so I rely on mypy strict and tests.
- **Follow-up:** When would you still pick an ABC?
- **Follow-up answer:** When you want shared implementation (template methods) or runtime
  `isinstance` guarantees at plugin-loading boundaries — e.g. `LangChainChatProvider` is a
  concrete base class because Bedrock and Azure share the invocation and token-usage logic.

### Q2. How do you handle timeouts for synchronous SDK calls in Python?
- **Concise:** Run the call in a thread pool and wait on the future with a timeout.
- **Senior:** `call_with_timeout` in `app/core/resilience.py` submits to a bounded
  `ThreadPoolExecutor` and uses `future.result(timeout=…)`. The caveat is that Python can't kill
  a thread, so the underlying call keeps running; that's why SDK-level timeouts are also set
  (`timeout=` on the LangChain clients) and the pool is bounded. With an async stack I'd use
  `asyncio.wait_for` and async clients.
- **Follow-up:** What's the risk of the thread-based approach under load?
- **Follow-up answer:** Hung calls occupy pool threads; if the provider stalls, the pool
  saturates and new calls queue. Mitigations: SDK timeouts, bounded pool, circuit breaker,
  and metrics on timeout counts.

### Q3. Why Python 3.12 specifically?
- **Concise:** Modern typing (PEP 695 generics, `StrEnum`), performance improvements and
  better error messages.
- **Senior:** The code uses PEP 695 generic syntax (`def retry_call[R](...)`,
  `class CallOutcome[R]`), `StrEnum` for statuses that serialise cleanly, and `itertools.pairwise`.
  3.12 is well supported by FastAPI, Pydantic v2, Chroma and LangChain; pinning `<3.13` avoids
  untested wheels for native dependencies.
- **Follow-up:** How do you keep builds reproducible across machines?
- **Follow-up answer:** `requirements.lock` generated by `uv pip compile --universal` for 3.12;
  CI and Docker install from the lock, then install the package itself.

### Q4. How do you make IDs and hashes deterministic?
- **Concise:** Hash canonical representations — sorted-key JSON — with SHA-256.
- **Senior:** `app/core/hashing.py` has `stable_json` (sorted keys, compact separators) used for
  audit event hashes and prompt hashes; chunk IDs are content hashes of document ID, page, index
  and text, which makes indexing idempotent. Random IDs (`new_id`) are only used for entities
  that should be unique per occurrence, like workflow runs.
- **Follow-up:** What breaks determinism most often?
- **Follow-up answer:** Floats and datetimes serialised inconsistently, dict ordering in
  non-canonical serialisers, and timestamps inside hashed payloads. The audit hash includes the
  timestamp deliberately, but excludes fields derived from the hash itself.

## FastAPI

### Q5. How is dependency injection structured in the API?
- **Concise:** A container is built at startup and exposed via `Depends`; routes receive it
  typed.
- **Senior:** `create_app(settings, container)` builds the container in the lifespan handler and
  stores it on `app.state`; `ContainerDep` and role dependencies (`Viewer`, `Analyst`, `Reviewer`,
  `Admin`) are `Annotated` aliases in `app/api/deps.py`. Tests pass a pre-built container with
  fault-injecting mocks, so no monkeypatching is needed.
- **Follow-up:** Why not create services per request?
- **Follow-up answer:** Providers hold clients, connection pools and the vector store; creating
  them per request is slow and wasteful. They are thread-safe or guarded, and request-scoped
  data flows via arguments and `contextvars`.

### Q6. How do you return consistent errors?
- **Concise:** A domain exception hierarchy mapped to HTTP status codes by one exception handler.
- **Senior:** `DocIntelError` subclasses carry `error_type` and `http_status`
  (`app/core/errors.py`); the handler returns `{"error": {"type", "message"}, "request_id"}`.
  Unhandled exceptions return a generic 500 `internal_error` without leaking internals, while the
  stack trace is logged with the request ID.
- **Follow-up:** How does a client correlate an error to logs?
- **Follow-up answer:** The `X-Request-ID` header — accepted from the client if well-formed or
  generated — is returned in the response header and body and attached to every log line via
  `contextvars`.

### Q7. How do you handle large file uploads safely?
- **Concise:** Enforce a size limit while reading and validate content, not just the filename.
- **Senior:** The route reads at most `limit + 1` bytes so an oversized upload is rejected
  without buffering it all; then extension, `%PDF` magic bytes and PDF parsing are checked, and
  the file is stored under a generated ID via an atomic write. In production I'd put a body-size
  limit at the proxy and stream directly to object storage.
- **Follow-up:** Why not trust the `Content-Type` header?
- **Follow-up answer:** It's client-controlled. Magic-byte checks plus actually parsing the PDF
  are the real validation; the header is advisory.

### Q8. Sync or async route handlers — which did you choose and why?
- **Concise:** Sync handlers for blocking work, so FastAPI runs them in a threadpool.
- **Senior:** The pipeline uses blocking libraries (pypdf, Tesseract, SQLAlchemy sync, boto3).
  Declaring those routes `def` lets Starlette offload them to its threadpool instead of blocking
  the event loop. Going fully async would need async DB and HTTP clients end to end; the bigger
  win is moving processing to background workers.
- **Follow-up:** What happens if you mark a blocking handler `async def`?
- **Follow-up answer:** It runs on the event loop and blocks every other request during the
  blocking call — a classic latency cliff.

## AWS Bedrock

### Q9. Why Bedrock as the primary provider?
- **Concise:** Managed access to Claude inside AWS with IAM auth, regional control and no
  separate API keys.
- **Senior:** For a financial institution already on AWS, Bedrock keeps inference within the
  account's security boundary, supports VPC endpoints, CloudTrail logging and IAM least
  privilege, and AWS states that prompts are not used to train models. The integration is
  `ChatBedrockConverse` behind `LLMProvider`, so the choice is reversible.
- **Follow-up:** What IAM permissions does the service need?
- **Follow-up answer:** `bedrock:InvokeModel` scoped to the specific model ARNs (chat and
  embeddings) and, if Textract is used, `textract:DetectDocumentText`. The README has the policy.

### Q10. How do you handle Bedrock throttling?
- **Concise:** Retry with exponential backoff, bounded attempts.
- **Senior:** The gateway retries retryable `ProviderError`s with backoff (0.5s × 2ⁿ, capped at
  8s, 2 retries by default), and the LangChain client's own retries are disabled so there is one
  retry policy. After exhaustion the document routes to review with `retries_exhausted` rather
  than failing silently. At scale: provisioned throughput, client-side rate limiting and a queue
  to smooth bursts.
- **Follow-up:** Why disable the SDK's built-in retries?
- **Follow-up answer:** Nested retries multiply attempts and latency unpredictably, and hide
  retry counts from our metrics. One policy in one place is observable and testable.

### Q11. Converse API vs InvokeModel — why Converse?
- **Concise:** Converse is a model-agnostic message API; InvokeModel takes model-specific JSON.
- **Senior:** Converse normalises messages, system prompts and token usage across Bedrock
  models, so switching Claude versions or families doesn't change request code; usage metadata
  flows into the invocation ledger. InvokeModel is still useful for features not yet exposed in
  Converse.
- **Follow-up:** How do you track token usage?
- **Follow-up answer:** The adapter reads `usage_metadata` from the LangChain response; if absent
  it estimates from character counts and marks `tokens_estimated=true` so cost reports stay
  honest.

### Q12. How would you run Bedrock privately?
- **Concise:** VPC interface endpoints (PrivateLink) for Bedrock runtime.
- **Senior:** Private subnets with a `bedrock-runtime` VPC endpoint and an endpoint policy
  restricting models, no internet egress, IAM role on the task, CloudTrail for API calls and
  region pinning for data residency.
- **Follow-up:** Does Bedrock log prompt content?
- **Follow-up answer:** Not by default; model-invocation logging is opt-in and, if enabled, must
  go to an encrypted, access-controlled destination because it contains document content.

## Claude

### Q13. How do you get reliable JSON out of Claude?
- **Concise:** Clear schema instructions, temperature 0, extract and validate the JSON, repair
  on failure.
- **Senior:** Prompts ask for exactly one JSON object with named fields; the gateway's
  `extract_json_object` tolerates code fences and surrounding prose, validates into a Pydantic
  model, and on failure sends one repair re-prompt including the validation error. Malformed
  output after repair becomes a typed error that routes to review. Native tool use is the next
  step for stronger guarantees.
- **Follow-up:** Why only one repair attempt?
- **Follow-up answer:** If the model fails twice on the same input, more retries mostly add cost
  and latency; the case is better handled by a human, and the failure rate is tracked as
  `llm_output_invalid_total`.

### Q14. Why temperature 0?
- **Concise:** Minimises randomness for extraction and classification.
- **Senior:** Extraction and grounded answering are not creative tasks; low temperature improves
  repeatability and makes evaluation meaningful. It is not a determinism guarantee — providers
  can still vary slightly — so evaluation uses aggregate metrics and tolerance, not exact output
  matching.
- **Follow-up:** When would you raise it?
- **Follow-up answer:** For generating paraphrases for test data or diverse candidate answers
  for self-consistency voting — never in the production extraction path.

### Q15. How do you handle Claude's context window with long documents?
- **Concise:** Truncate or chunk inputs; use retrieval for Q&A.
- **Senior:** Classification uses a bounded excerpt (`max_chars`); extraction currently sends
  all page-delimited text (`[page N]` markers), which is fine for statement-sized documents; Q&A
  uses retrieval so only top-k chunks go to the model. For very long documents I'd extract per
  section and merge with conflict detection — the pipeline already surfaces
  `conflicting_values` — and add a size limit that routes oversize documents to review.
- **Follow-up:** Isn't "stuff everything in the long context" simpler?
- **Follow-up answer:** It's simpler but more expensive, slower, loses citation precision, and
  models attend unevenly across very long contexts. Retrieval keeps cost bounded and answers
  traceable.

### Q16. How do you manage Claude model version upgrades?
- **Concise:** Pin model IDs and evaluate before switching.
- **Senior:** The model ID is configuration; every extraction, answer and invocation records the
  model name and prompt version; the evaluation gate runs against the new model with its own
  baseline; the drift monitor surfaces version changes as `info`. Roll out via shadow or canary.
- **Follow-up:** What if the new model is better on average but worse on one document type?
- **Follow-up answer:** Slice metrics by type (the evaluation reports per-class metrics); block
  or route that type to the old model until prompts are tuned — possible because the provider
  choice is per configuration.

## Azure OpenAI

### Q17. Why support Azure OpenAI as well?
- **Concise:** Vendor diversification and customer or regional requirements.
- **Senior:** Concentration risk on one provider is a real operational-resilience concern for
  regulated firms. `AzureOpenAIProvider` implements the same interface; switching is one env
  var, and the same evaluation harness quantifies quality differences.
- **Follow-up:** Would you do automatic failover between providers?
- **Follow-up answer:** Only with per-provider baselines showing acceptable quality, identical
  guardrails, and data-processing agreements for both. Otherwise failover could silently lower
  quality — in finance, routing to review is often the safer fallback.

### Q18. What's different about Azure OpenAI configuration?
- **Concise:** You call deployments, not models, with an endpoint, API version and key or
  Entra ID.
- **Senior:** Config includes endpoint, API version, chat and embedding deployment names; the key
  is a `SecretStr`. Missing values raise `ProviderConfigurationError` at start-up. In production
  I'd prefer Entra ID managed identity over keys.
- **Follow-up:** How do you avoid logging the key?
- **Follow-up answer:** `SecretStr` masks it in repr; the logging filter redacts credential-like
  keys; the key is never part of a log payload.

### Q19. Would prompts need to change between Claude and GPT models?
- **Concise:** Sometimes; the same prompt usually works but quality can differ.
- **Senior:** The prompts are provider-neutral (system + user, JSON output). Differences show up
  in formatting habits and refusal behaviour, handled by the gateway's JSON extraction. If a
  provider needed a variant, the registry supports a new prompt version, evaluated separately.
- **Follow-up:** How would you store provider-specific prompts?
- **Follow-up answer:** As separate versioned prompt files selected by provider in config, each
  with its own hash lock entry and baseline.

## RAG

### Q20. Walk through your RAG pipeline.
- **Concise:** Screen question → retrieve top-k → prompt with context → validate answer →
  check citations and groundedness → return or refuse.
- **Senior:** `app/rag/service.py`: injection check before any retrieval; retrieval with
  document filter, top-k and score threshold; empty retrieval → refusal "insufficient evidence";
  context formatted with chunk IDs and marked untrusted; model returns JSON with answer and cited
  IDs; invalid IDs dropped with a warning; groundedness computed deterministically; prohibited
  claims blocked; confidence = 0.6 × groundedness + 0.4 × retrieval strength; low confidence or
  weak grounding → review case.
- **Follow-up:** Why check injection before retrieval rather than after?
- **Follow-up answer:** A blocked question shouldn't cost a retrieval or model call, and the
  refusal is audited. Document-borne injection is handled separately at ingestion and in context
  assembly.

### Q21. How do you decide when to refuse?
- **Concise:** When retrieval finds nothing above the threshold, or the answer can't be grounded.
- **Senior:** Three refusal paths: guardrail block, insufficient evidence (no chunk above
  `retrieval_min_score`), and unsupported output (groundedness failure on figures or a prohibited
  claim). Refusal quality is measured: correct-refusal rate (1.0 on the mock set) and
  false-refusal rate (0.167), so the threshold trade-off is visible.
- **Follow-up:** How would you reduce false refusals?
- **Follow-up answer:** Better embeddings and hybrid search to raise recall, tune the threshold
  per embedding model on labelled data, and query rewriting for vague questions.

### Q22. How do you evaluate retrieval separately from generation?
- **Concise:** Labelled relevant chunks per question; compute precision/recall@k, MRR, hit rate.
- **Senior:** `evals/datasets/retrieval.jsonl` labels expected pages and target documents; the
  runner computes precision@k, recall@k, hit rate, MRR, document hit rate and context relevance.
  Generation is scored separately (completeness, groundedness, citation correctness). Separation
  tells you whether to fix the retriever or the prompt.
- **Follow-up:** Your precision@k is 0.27 — is that bad?
- **Follow-up answer:** With k=4 and usually one relevant chunk per question, the ceiling is
  about 0.25–0.5. Recall and MRR matter more for answer quality here; precision mainly affects
  context cost and noise.

### Q23. How do you handle multi-document questions?
- **Concise:** Use the corpus endpoint with metadata filters.
- **Senior:** `POST /ask` searches across documents with optional filters (`document_type`,
  `extraction_method`); citations carry document IDs. Aggregations ("total across all
  invoices") should come from structured extraction data, not RAG — LLMs are bad at arithmetic
  over retrieved snippets.
- **Follow-up:** How would you answer "sum of all invoice totals for vendor X"?
- **Follow-up answer:** Query the extracted, validated fields in the database (text-to-SQL over
  a governed view, or a fixed report), and use RAG only for explanation and citations.

### Q24. What is context assembly and why does it matter?
- **Concise:** Formatting retrieved chunks into the prompt.
- **Senior:** Each chunk is labelled with its ID and page, wrapped in delimiters and declared
  untrusted; suspicious content inside chunks adds a warning. Ordering by score and dropping
  low-score chunks reduces distraction. Good assembly is what makes citation binding possible.
- **Follow-up:** Would you include extracted fields in the context?
- **Follow-up answer:** Possibly, as a separate labelled block — useful for direct field
  questions — but only fields that passed validation or review, and still citable to evidence
  snippets.

## Embeddings

### Q25. Why a hashing embedder in mock mode?
- **Concise:** Offline, deterministic, no model download or API cost.
- **Senior:** It makes retrieval testable in CI with stable results. It's lexical (hashed
  unigrams and bigrams, sublinear TF, L2-normalised), so it can't match "profit" with
  "earnings" — which is documented, and why production uses Titan or Azure embeddings. For
  financial term queries, lexical matching is surprisingly competitive.
- **Follow-up:** Why not a small local sentence-transformer?
- **Follow-up answer:** It adds a heavy dependency (torch) and a model download to CI and the
  image for a demo corpus; the abstraction lets you add one without code changes elsewhere.

### Q26. What happens when you change embedding models?
- **Concise:** Old vectors are incompatible; you must re-embed.
- **Senior:** Chroma collections are namespaced by a hash of the embedding model name
  (`chunks_<hash>`), so a new model writes to a new collection and never mixes vector spaces.
  Re-indexing means reprocessing documents; in production, a background re-index job with
  dual-read cut-over.
- **Follow-up:** How do you validate the new model before cutting over?
- **Follow-up answer:** Run retrieval evaluation against both collections and compare
  recall@k/MRR; only switch when the new model meets the baseline.

### Q27. Cosine similarity vs dot product vs Euclidean?
- **Concise:** For normalised vectors, cosine and dot product rank identically; Euclidean is
  monotonic with them.
- **Senior:** Chroma is configured for cosine space and similarity is reported as 1 − distance.
  The hashing embeddings are L2-normalised, so rankings are consistent across metrics. Scores
  are model-specific — thresholds must be re-tuned when the model changes.
- **Follow-up:** Why are your similarity scores so low (~0.13)?
- **Follow-up answer:** Hashed lexical vectors over short questions share few features with
  long chunks, so absolute scores are low even for correct matches; ranking is what matters,
  and the threshold (0.12) was set on that scale.

### Q28. How would you embed tables?
- **Concise:** Serialise rows with headers, or embed a textual summary.
- **Senior:** Convert each table row to "header: value" text, keep the table as one chunk unit
  when small, and store structured cells separately for exact lookup. Numeric questions should
  prefer structured data over vector similarity.
- **Follow-up:** Where does that fit in this codebase?
- **Follow-up answer:** In the chunker (`app/retrieval/chunking.py`) as a table-aware strategy,
  fed by a layout-aware OCR provider such as Textract `AnalyzeDocument`.

## Vector databases

### Q29. Why Chroma?
- **Concise:** Embedded, persistent, simple API, metadata filters, no server needed.
- **Senior:** It keeps the local stack single-container while exercising real vector-store
  behaviour (persistence, cosine distance, `where` filters, upsert/delete). The `VectorStore`
  protocol isolates it; ADR-002 records that production should move to a managed, multi-node
  store with tenant isolation.
- **Follow-up:** What are Chroma's limits here?
- **Follow-up answer:** Single-node embedded mode, a single writer, no built-in multi-tenancy
  or row-level auth. Fine for a demo; not for multi-instance deployment.

### Q30. How do you keep the index consistent with the database?
- **Concise:** Idempotent upserts keyed by deterministic chunk IDs; reprocessing replaces chunks.
- **Senior:** Chunk IDs are content hashes, so re-indexing the same text is a no-op, and
  reprocessing deletes a document's old chunks before upserting new ones. A crash between DB
  commit and index write leaves the workflow in an in-progress or `FAILED` state that can be
  retried. In production: an outbox pattern or indexing as a separate idempotent job.
- **Follow-up:** What about deletions for retention?
- **Follow-up answer:** `delete_document` exists on both stores and the document store; a
  retention job would delete from storage, index and DB and write an audit event.

### Q31. pgvector vs OpenSearch vs a dedicated vector DB?
- **Concise:** pgvector for simplicity with Postgres; OpenSearch for hybrid search at scale;
  dedicated DBs for very large vector workloads.
- **Senior:** If the metadata is already in Postgres, pgvector gives transactional consistency
  and SQL filters. OpenSearch adds BM25 + k-NN hybrid search and mature operations on AWS.
  Dedicated stores win at hundreds of millions of vectors. For this workload — per-document
  filtered retrieval — pgvector or OpenSearch is sufficient.
- **Follow-up:** How do you enforce tenant isolation in a shared index?
- **Follow-up answer:** A mandatory tenant filter injected server-side (never from the client),
  or index-per-tenant for strong isolation, plus tests that assert no cross-tenant results.

## LangChain / LlamaIndex

### Q32. How do you use LangChain, and why so narrowly?
- **Concise:** Only for provider adapters, prompt templates and the text splitter.
- **Senior:** LangChain gives maintained integrations for Bedrock and Azure; I avoid chains and
  agents so control flow, retries, validation and logging stay in my code where they're
  testable and auditable (ADR-001). The seam means LangChain could be removed without touching
  business logic.
- **Follow-up:** Where does LlamaIndex fit?
- **Follow-up answer:** As a second retrieval engine behind the same `RetrieverProtocol`
  (`DOCINTEL_RAG_ENGINE=llamaindex`, optional extra). A `VectorStoreIndex` retriever reads the
  existing Chroma or in-memory store through a small adapter, so ingestion, citation binding,
  thresholds and guardrails stay in my code. Parity tests check filters, document scoping and the
  similarity threshold, and unsupported filters raise instead of silently widening the search.
  Live with Titan it returned the same ranked top-4 chunks and scores as the native engine for
  all 51 evaluation queries, for about 1 ms of overhead per query (ADR-001 amendment, README
  engine comparison).

### Q33. What are the risks of heavy framework adoption in regulated systems?
- **Concise:** Hidden behaviour, fast-moving APIs, harder audits.
- **Senior:** Implicit retries, prompt mutations and callbacks make it hard to state exactly what
  was sent to a model. Breaking changes are frequent. Keeping the framework at the adapter layer,
  with prompts owned and hashed in the repo, keeps the audit story simple.
- **Follow-up:** How do you prove what prompt was sent?
- **Follow-up answer:** Each invocation records prompt name, version and template hash; the
  template is in version control; variables are the document text and question, which are
  stored.

### Q34. How did you test the LangChain adapters without credentials?
- **Concise:** With LangChain's fake chat models injected into the adapters.
- **Senior:** The adapters accept an optional `chat_model`; tests pass fake models to verify
  message construction, response parsing and token-usage handling. The real clients are only
  constructed when no model is injected, after config validation.
- **Follow-up:** Does that prove the Bedrock call works?
- **Follow-up answer:** No — it proves our side of the contract. I did run the Azure adapter live
  against `gpt-4.1-mini`, and the evaluation suite immediately found things the fakes couldn't: a
  ground-truth label biased toward the mock, an ambiguous date rule in the prompt, a mis-masked
  IBAN, and a conflict check that was case-sensitive. Bedrock still needs that run, and a
  scheduled contract test with real credentials should catch provider-side changes.

## Document intelligence

### Q35. How do you define extraction schemas per document type?
- **Concise:** In YAML config: fields, types, required flags and validation rules.
- **Senior:** Each type has a Pydantic model in `app/extraction/schemas.py` (`InvoiceFields`,
  `BankStatementFields`, …). Field descriptions, kinds (amount, date, currency, percent, masked
  account, text) and required flags live on the model and are the single source of truth: the
  extraction prompt receives the descriptions, coercion uses the kinds, validation uses the
  required flags. Cross-field rules are in `app/extraction/validation.py`.
  `config/document_types.yaml` only holds keywords and label synonyms for the offline mock; a
  test asserts every schema field has synonyms there.
- **Follow-up:** How do you version schema changes?
- **Follow-up answer:** Schema changes are code changes reviewed in a PR; because field
  descriptions are rendered into the extraction prompt, a schema change also changes what the
  model sees, so it is evaluated through the gate. Results record the prompt version; adding an
  explicit schema version to `ExtractionResult` is a sensible next step.

### Q36. What validation rules do you apply?
- **Concise:** Type/format checks and cross-field arithmetic.
- **Senior:** `app/extraction/validation.py`: per-field checks (required fields, ISO 4217
  currency codes, date/period plausibility, percent range, numeric amounts, masked account
  format), evidence verification, conflicting candidates, and cross-field rules per type —
  subtotal + tax = amount due, assets = liabilities + equity, opening balance + credits − debits
  = closing balance, operating income consistency, net income ≤ revenue, fund fee range —
  within a tolerance. Failures produce `ValidationIssue`s with severity and route to review.
- **Follow-up:** Why a tolerance?
- **Follow-up answer:** Rounding in source documents; an exact-equality rule would flag correct
  documents. The tolerance is configurable and small.

### Q37. How do you verify that extracted values actually come from the document?
- **Concise:** Require an evidence quote and check it appears in the page text.
- **Senior:** The model returns a snippet per field; the extractor checks it verbatim
  (whitespace-normalised) against the page text and marks the entity `verified`. Unverified
  evidence is a review reason. This catches hallucinated fields cheaply and gives reviewers the
  exact location.
- **Follow-up:** What if the value is right but the quote is slightly off?
- **Follow-up answer:** It goes to review as unverified — a deliberate false positive preferred
  over silently accepting unverifiable values. Fuzzy matching with a high threshold is a
  possible refinement.

### Q38. How do you handle conflicting values in one document?
- **Concise:** Detect alternatives and flag them for review.
- **Senior:** The extractor records alternative candidates per field; conflicting candidates
  produce `conflicting_values`. The Granite balance sheet sample exercises this and is corrected
  through the review API in the demo.
- **Follow-up:** Could you auto-resolve conflicts?
- **Follow-up answer:** Sometimes with rules (prefer the "Total" row, prefer the current-period
  column), but auto-resolution needs evaluation evidence; until then humans decide.

## OCR

### Q39. How do you decide when to OCR?
- **Concise:** When the native text layer is missing or too sparse.
- **Senior:** `pypdf` text is tried first; if characters per page fall below a threshold, pages
  are rendered and OCR'd. This avoids OCR's cost and error rate on digital PDFs. The method is
  recorded on the document (`native_pdf`, `ocr_tesseract`, `ocr_textract`) and in chunk
  metadata.
- **Follow-up:** What about PDFs with a bad text layer (garbled encoding)?
- **Follow-up answer:** Add a quality heuristic (ratio of dictionary words or valid characters)
  to trigger OCR even when text exists; currently only sparsity triggers it.

### Q40. Tesseract, Textract or a vision model?
- **Concise:** Tesseract is free and local; Textract is managed and more accurate on complex
  layouts; a multimodal model reads noisy scans best but costs a model call per page.
- **Senior:** All three implement the OCR provider interface. Tesseract suits offline/dev and
  sensitive deployments where data can't leave the host; Textract offers better accuracy,
  tables and forms, at a per-page cost. Vision OCR (`bedrock_vision` with Claude,
  `azure_vision` with an Azure deployment such as gpt-4.1-mini) sends each rendered page as an
  image with a versioned transcription prompt, and Tesseract cross-checks the numbers when it is
  installed (ADR-013). On three scored scans, two deliberately degraded, both vision models had a
  character error rate of 0.000 against Tesseract's 0.104, at about 3 s and under a cent a page.
  Three synthetic pages prove the integration, not production accuracy, so OCR'd documents still
  go to review. `auto` picks Tesseract if installed.
- **Follow-up:** Can a vision model hallucinate text?
- **Follow-up answer:** Yes, it can produce fluent text that isn't on the page, which a classic
  OCR engine doesn't. That's why the numbers are cross-checked against Tesseract, extraction
  evidence must still be found in the transcribed text, and every OCR'd document is reviewed.
  Image bytes are never logged; their hashes are.
- **Follow-up:** How did you test Textract without AWS?
- **Follow-up answer:** A stub client returning a realistic `DetectDocumentText` response
  (`FakeTextract` in `tests/support.py`), injected into the provider; the rendering and
  line-assembly path is real.

### Q41. Why route every OCR'd document to review?
- **Concise:** OCR errors on digits are common and consequential.
- **Senior:** A misread 8 → 3 still passes type checks. Until per-field OCR confidence and
  calibrated thresholds exist, reviewing OCR documents is the conservative default, configurable
  via `review_ocr_documents`.
- **Follow-up:** How would you reduce that review load?
- **Follow-up answer:** Use word-level OCR confidence, require arithmetic rules to pass, and
  auto-approve only when all fields are high-confidence and consistent — after measuring the
  error-escape rate on a sample.

## Agentic AI

### Q42. Is this an "agent"? Why or why not?
- **Concise:** It's an agentic workflow: AI performs steps inside a deterministic orchestrator,
  not an autonomous tool-choosing loop.
- **Senior:** The model classifies, extracts and answers; the code decides transitions,
  retries, and escalation. That gives enumerable paths, reproducibility and a clean audit trail
  — which regulators and model-risk teams expect. Autonomy is added only where it's bounded and
  evaluated.
- **Follow-up:** Where would you allow tool use?
- **Follow-up answer:** Inside a step with a fixed tool set and validated arguments — e.g. a
  vendor-master lookup to validate an invoice vendor — with every call logged and the output
  still passing validation.

### Q43. What are the risks of autonomous agents in finance?
- **Concise:** Unpredictable actions, prompt injection leading to harmful actions, hard audits.
- **Senior:** An agent that can act (pay, email, update records) turns prompt injection from
  "bad text" into "bad action". Non-determinism complicates reproducibility and testing. Hence:
  the model has no actions here; payments or approvals are human decisions.
- **Follow-up:** How would you make an action-taking agent safe?
- **Follow-up answer:** Least-privilege tools, allow-listed parameters, human approval for
  consequential actions, rate limits, full logging, and red-team testing of injection scenarios.

### Q44. How does the orchestrator handle partial failures?
- **Concise:** Soft failures accumulate as review reasons; hard failures move to `FAILED`.
- **Senior:** Low confidence, rule failures or injection flags don't stop the pipeline — it
  continues so the reviewer gets a complete picture in one consolidated case. Hard failures
  (unreadable PDF, vector-store error) move to `FAILED` with the error recorded; retry
  transitions `FAILED → INGESTED`.
- **Follow-up:** Why not stop at the first problem?
- **Follow-up answer:** Stopping early means multiple review rounds for one document and less
  context for the reviewer. The exception is OCR unavailable, where there's no text to continue
  with.

## Structured outputs

### Q45. How do you validate LLM output?
- **Concise:** Parse JSON and validate with Pydantic models.
- **Senior:** The gateway extracts the first JSON object, validates into the operation's response
  model (e.g. `ClassificationResponse`, extraction response, `RAGModelOutput`), and on failure
  re-prompts once with the error. Field values are then coerced by type-specific logic.
  `answers.schema_validity` is a gated metric at 1.0.
- **Follow-up:** Why not rely on the provider's JSON mode?
- **Follow-up answer:** JSON mode guarantees syntax, not your schema or semantics; validation is
  still required, and keeping it in the gateway makes behaviour identical across providers.

### Q46. How do you coerce financial numbers?
- **Concise:** Normalise formatting (commas, currency symbols, parentheses for negatives) then
  parse to float/Decimal.
- **Senior:** `coerce_field_value` (via `normalize_number` in `app/core/text.py`) parses
  "(1,234.00)" as negative, strips symbols and thousands separators, and leaves unparseable
  values as strings so validation flags them ("amount is not numeric") instead of guessing.
  Dates are kept as the document states them and checked for plausibility (known formats or a
  period containing a year). Failed coercion is a validation issue, not a silent null.
- **Follow-up:** Float or Decimal for money?
- **Follow-up answer:** Decimal for accounting systems of record. Here values are floats with
  tolerance-based comparison because this is extraction and validation, not ledger arithmetic;
  a production integration should hand off Decimals.

### Q47. What if the model returns extra fields?
- **Concise:** Ignore or reject them depending on the schema config.
- **Senior:** Extraction only keeps fields defined in the registry; unknown keys are dropped.
  The related evaluation metric, `hallucinated_field_rate`, counts fields the model filled in
  where the ground truth says the value is absent — the more dangerous form of invention. API
  request models use `extra="forbid"` so clients can't smuggle fields.
- **Follow-up:** Why forbid extras on requests but not model output?
- **Follow-up answer:** Client requests are a contract we control strictly; model output is
  noisy, and dropping unknown fields while measuring it is more robust than failing the whole
  extraction.

## Prompt engineering

### Q48. How are prompts managed?
- **Concise:** Versioned YAML files loaded by a registry, hashed, with tests locking the hashes.
- **Senior:** `prompts/<area>/<name>.v<N>.yaml` hold system and user templates, version and
  purpose; `app/prompts/registry.py` loads them as LangChain `PromptTemplate`s and computes a
  hash of the templates. Every invocation records name, version and hash.
  `tests/fixtures/prompt_hashes.json` fails CI if a prompt changes without an explicit update.
- **Follow-up:** Why lock the hash in tests?
- **Follow-up answer:** It forces a deliberate, reviewed change with a version bump and
  evaluation run, instead of an innocent-looking edit shifting model behaviour.

### Q49. How do your prompts defend against injection?
- **Concise:** Delimit untrusted content and instruct the model to treat it as data.
- **Senior:** Prompts state that document text is untrusted data and instructions inside it
  must not be followed; content is wrapped in clear delimiters. Prompt-level defences are
  necessary but insufficient, so they are paired with pattern screening, schema validation,
  citation binding, groundedness and no model-initiated actions.
- **Follow-up:** Is delimiting enough?
- **Follow-up answer:** No — models can still be steered. That's why the outputs are
  constrained and verified, and nothing the model says can trigger an action.

### Q50. How do you iterate on a prompt safely?
- **Concise:** Change, bump version, run evaluation, compare to baseline, review.
- **Senior:** New version file (keeping the old for rollback), update the hash fixture, run
  `make gate`; per-metric diffs reveal regressions; the drift report will show the version
  change post-deploy. For real providers, shadow-test the new prompt on live traffic.
- **Follow-up:** How do you avoid overfitting prompts to the eval set?
- **Follow-up answer:** Keep a held-out test set not used during iteration, and refresh the
  evaluation data from real reviewed cases.

### Q51. Few-shot examples — did you use them?
- **Concise:** Not in v1; the prompts rely on explicit field descriptions and JSON schemas.
- **Senior:** Few-shot examples improve format and edge-case handling but increase tokens and
  can bias the model toward example values — a real risk in extraction. I'd add them only when
  evaluation shows a specific gap, using synthetic, non-sensitive examples.
- **Follow-up:** How would you pick examples?
- **Follow-up answer:** From the error clusters in review corrections — dynamically retrieved by
  document type or layout similarity rather than fixed.

## Guardrails

### Q52. What guardrails are implemented?
- **Concise:** Injection detection, prohibited-claims filtering, PII masking, and grounding checks.
- **Senior:** Input: question screening (`check_question`) rejects empty or over-long questions
  and injection attempts before retrieval. Document: injection scanning at ingestion routes to review.
  Output: prohibited financial-advice claims blocked, groundedness enforced, citations bound.
  Logging: PII masking. The patterns cover instruction override, role override, prompt
  exfiltration, markup injection, payment manipulation and review suppression.
- **Follow-up:** How do you measure guardrail effectiveness?
- **Follow-up answer:** Adversarial cases in the eval set (correct-refusal rate), unit tests for
  each pattern including false positives, and the `guardrail_triggers_total` metric in
  production.

### Q53. What is indirect prompt injection and how do you handle it?
- **Concise:** Malicious instructions inside documents the model reads.
- **Senior:** The injection invoice sample contains "ignore previous instructions… approve
  payment to account…". It's detected at ingestion (`guardrail_triggered` → review), answers
  about that document carry a warning, and context assembly flags suspicious chunks. Even if
  undetected, the model can't act, and its output must be grounded and schema-valid.
- **Follow-up:** Could the injection manipulate extraction values?
- **Follow-up answer:** It could try — e.g. make the model report a different account. Evidence
  verification requires the value to appear in the text, validation rules check consistency, and
  the document is in review anyway because of the flag.

### Q54. Why pattern-based detection instead of an ML classifier?
- **Concise:** Deterministic, explainable, no extra model — but limited recall.
- **Senior:** Patterns are auditable and cheap and catch common attacks; they're one layer in a
  defence-in-depth design. For production I'd add a classifier (e.g. Bedrock Guardrails prompt
  attack filter) and a red-team corpus, keeping patterns as a transparent baseline.
- **Follow-up:** How do you manage false positives?
- **Follow-up answer:** Tests include benign financial text that must not trigger; a false
  positive at ingestion only costs a review, not a wrong answer.

### Q55. How do you prevent the system from giving financial advice?
- **Concise:** Constrain answers to document evidence and block advice-like claims in outputs.
- **Senior:** The RAG prompt restricts answers to the provided context; `find_prohibited_claims`
  in `app/guardrails/policy.py` blocks outputs containing phrases like "you should buy",
  "guaranteed returns" or "risk-free investment", turning them into a refusal with a review case.
  Advice-seeking *questions* are not blocked up front — they typically fail grounding because
  documents don't contain recommendations. This is a product-scope control, not legal
  compliance; an intent classifier on questions is a sensible addition.
- **Follow-up:** What if a document itself contains "guaranteed returns"?
- **Follow-up answer:** The current filter is phrase-based, so it blocks the answer even when it
  is a faithful quote, and the case goes to review — a deliberate false positive. A refinement
  is to allow such phrases only when they appear verbatim in the cited evidence and to present
  them as attributed quotes.

## Human-in-the-loop

### Q56. When does a document go to human review?
- **Concise:** When any confidence, validation, grounding, safety or reliability check fails.
- **Senior:** Fifteen explicit reasons (`ReviewReason` in `app/domain/enums.py`): low/unknown
  classification, low extraction confidence, schema or rule failures, missing required fields,
  unverified evidence, conflicting values, OCR used/unavailable, injection detected, retries
  exhausted, and for answers insufficient evidence, weak grounding or low confidence. Reasons are
  collected across the pipeline and a single case is opened per document.
- **Follow-up:** How did you pick the thresholds (0.70 classification, 0.60 extraction)?
- **Follow-up answer:** As conservative defaults validated on the sample set; they are
  configurable. In production they'd be tuned on labelled data to hit a target error-escape rate
  at an acceptable review rate.

### Q57. What does a reviewer see?
- **Concise:** The reasons, details, the model's original output, and model/prompt versions.
- **Senior:** `ReviewCase` includes reasons, human-readable details (e.g. which rule failed with
  values), `original_output` (classification, extraction with evidence snippets and pages, or the
  answer with citations), model and prompt versions, and timestamps. The API is the reviewer
  contract; a UI would render page images with highlighted evidence.
- **Follow-up:** How do you keep reviewers from rubber-stamping?
- **Follow-up answer:** Specific reasons rather than "please review", sampling approved cases for
  QA, tracking approval rates per reviewer, and maker-checker for high-value items.

### Q58. How are corrections applied safely?
- **Concise:** Validate corrections through the same schema and rules, then store a new version.
- **Senior:** `_apply_field_corrections` coerces values with the type's Pydantic model, runs
  `validate_field` (e.g. rejects "DOLLARS" as a currency — a bug caught by tests and fixed),
  re-runs cross-field validation, stores a new `ExtractionResult` with `corrected_by_review_id`,
  and marks corrected fields `CORRECTED`. Invalid input returns 422; the original model output
  is preserved.
- **Follow-up:** What if the reviewer changes the document type?
- **Follow-up answer:** The orchestrator re-runs extraction for the new type with the reviewer's
  type as a forced classification (confidence 1.0, provider "human"), then resolves the case.

### Q59. How is reviewer identity established?
- **Concise:** From the authenticated API key when auth is on.
- **Senior:** With auth enabled, the principal's ID (`key-<sha10>`) is used and any
  `reviewer_id` in the body is ignored — preventing impersonation. In local mode the body value is
  used and labelled as a placeholder. Every decision is audited with actor, comment and changes.
- **Follow-up:** What's missing for production?
- **Follow-up answer:** Real user identities via SSO/OIDC, segregation of duties (the uploader
  can't approve), and four-eyes approval for material corrections.

### Q60. How do human decisions feed back into the system?
- **Concise:** They become labelled data for evaluation, monitoring and potential fine-tuning.
- **Senior:** Correction and rejection rates are drift metrics; corrected extractions are
  ground-truth candidates for the evaluation set; clusters of corrections point to prompt or
  schema fixes. The fine-tuning pathway document describes how they'd become a training set;
  the experiment in this repository uses synthetic data instead (Q113).
- **Follow-up:** Any risk in using reviewer corrections as ground truth?
- **Follow-up answer:** Reviewer error and bias. Double-annotate a sample, measure agreement,
  and adjudicate disagreements before promoting corrections into the gold set.

## AI evaluation

### Q61. What does your evaluation harness measure?
- **Concise:** Classification, extraction, retrieval, answer quality and workflow routing.
- **Senior:** Classification accuracy, macro-F1, per-class P/R and confusion matrix; extraction
  field accuracy, normalised match, missing/hallucinated/invalid rates; retrieval P@k, R@k, hit
  rate, MRR, document hit rate, context relevance; answers completeness, groundedness, citation
  correctness, relevance, unsupported-statement rate, schema validity, correct/false refusal;
  workflow routing accuracy and review precision/recall. Optional LLM-judge groundedness.
- **Follow-up:** Which single metric matters most?
- **Follow-up answer:** For finance, the error-escape rate — wrong values that were *not*
  routed to review. Review recall approximates it; I'd make it explicit with a labelled set.

### Q62. Your mock scores are 1.0 — isn't that suspicious?
- **Concise:** Yes, and it's documented: synthetic data and mock rules were built together.
- **Senior:** Perfect scores show the pipeline, validators and metrics work end to end and
  deterministically; they say nothing about model accuracy. The informative signals are the
  imperfect metrics (three failing answer cases, low precision@k, false refusals), the
  regression gate, and that the same harness runs against Bedrock or Azure unchanged. ADR-006
  states this explicitly.
- **Follow-up:** How would you build a credible evaluation set?
- **Follow-up answer:** Sample real documents stratified by type, source and quality; double
  annotate; include hard cases (scans, multi-page, conflicts, injections); hold out a test split;
  refresh from reviewed production cases.

### Q63. How do you compare two prompt or model versions?
- **Concise:** Run both through the same harness and compare metrics with tolerances.
- **Senior:** Same dataset, same thresholds, per-slice breakdown, and the regression gate against
  the incumbent's baseline. For real models, repeat runs to estimate variance and use paired
  comparisons on the same items rather than aggregate deltas alone.
- **Follow-up:** How do you know a 2-point improvement is real?
- **Follow-up answer:** Bootstrap confidence intervals or a paired test (e.g. McNemar for
  per-item correctness); with small datasets, many differences aren't significant.

### Q64. How does LLM-as-judge fit in?
- **Concise:** An optional second opinion on groundedness in evaluation.
- **Senior:** With `eval_use_llm_judge`, a versioned judge prompt scores each answer's support;
  it complements the deterministic check, which misses paraphrase errors. The judge reads the full
  cited chunks, and `eval_judge_provider` lets another vendor's model judge (live: Claude's answers
  judged by gpt-4.1-mini, 1.00 on 20 answers). Judge calls are tagged `operation="judge"` and
  excluded from drift statistics.
- **How do you know it isn't a rubber stamp?** `scripts/judge_calibration.py` feeds it corrupted
  copies of real answers. It flagged 20/20 changed numbers, 12/12 negations and 20/20 appended
  claims, and none of the originals; the lexical check missed every negation. That is synthetic
  corruption, not agreement with human graders, which is still the next step.
- **Follow-up:** Why not use the judge in production?
- **Follow-up answer:** Cost and latency double, and the judge can be wrong or manipulated too.
  Deterministic checks are cheap and explainable; the judge is better as an offline or sampled
  monitor.

### Q65. How do you evaluate workflow routing?
- **Concise:** Compare actual outcome (READY / NEEDS_REVIEW / FAILED) against expected per
  document.
- **Senior:** Ground truth marks which documents should be reviewed (edge cases: scanned,
  injection, conflict, ambiguous memo) or fail (empty, malformed). The runner computes routing
  accuracy and review precision/recall — precision guards reviewer load, recall guards against
  risky documents slipping through.
- **Follow-up:** Which do you prioritise, review precision or recall?
- **Follow-up answer:** Recall, within an operational budget — a missed risky document costs more
  than an extra review.

## Hallucination

### Q66. How do you detect hallucinated numbers in answers?
- **Concise:** Every number in the answer must appear in the cited evidence.
- **Senior:** `check_groundedness` normalises numbers in answer and evidence and fails any
  sentence with a number not in evidence; it also requires ≥ 60% token support. Unsupported
  numbers make the answer a refusal or review case. It deliberately refuses to trust
  calculations — the prompt tells the model not to compute new figures.
- **Follow-up:** What about legitimate derived values like growth percentages?
- **Follow-up answer:** They'd be flagged. Derived figures should be computed deterministically
  from extracted fields and presented as calculations, not generated by the model.

### Q67. What types of hallucination matter in document AI?
- **Concise:** Invented values, wrong attribution, and unsupported claims.
- **Senior:** Fabricated fields (value not in document), misattribution (right number, wrong
  field or period), citation hallucination (invented chunk IDs), and unsupported synthesis.
  Controls map one-to-one: evidence verification, cross-field rules, citation binding,
  groundedness.
- **Follow-up:** Which is hardest to catch?
- **Follow-up answer:** Misattribution — the number exists in the document, so lexical checks
  pass. Cross-field rules and period-aware extraction help; reviewers catch the rest.

### Q68. Does RAG eliminate hallucination?
- **Concise:** No, it reduces it; models can still ignore or misread context.
- **Senior:** RAG supplies evidence but doesn't force its use. That's why the pipeline verifies
  outputs against the evidence and refuses when support is weak, rather than trusting the
  retrieval step.
- **Follow-up:** What reduces hallucination further?
- **Follow-up answer:** Better retrieval (less irrelevant context), constrained extractive
  answers, entailment checking, and refusing when evidence is thin.

## Testing

### Q69. Describe your test pyramid.
- **Concise:** Many unit tests, fewer integration tests, a set of API end-to-end tests.
- **Senior:** Unit tests cover pure logic (hashing, rules, guardrails, groundedness, metrics,
  drift, gateway retry and repair). Integration tests run the real workflow with the mock
  provider and in-memory stores on every sample PDF and failure mode. E2E tests drive the FastAPI
  app via `TestClient`, including auth. All ~250 tests run offline in under 15 seconds.
- **Follow-up:** What isn't covered?
- **Follow-up answer:** Live provider calls, concurrency and load, and container orchestration
  beyond the Docker smoke test.

### Q70. How do you test failure modes?
- **Concise:** Fault injection in the mock provider and stubs for other dependencies.
- **Senior:** `MockLLMProvider(fail_first_n=…, malformed_first_n=…, delay_s=…)` exercises
  retries, JSON repair, timeouts and `retries_exhausted`; a failing vector store tests `FAILED`
  routing; empty, malformed and encrypted PDFs test ingestion errors; OCR unavailable is tested by
  configuration. Each asserts the final status, review reasons and audit events.
- **Follow-up:** How do you keep timeout tests fast?
- **Follow-up answer:** Tiny timeouts (50 ms) with a slightly longer mock delay, and retry
  backoff set to zero in test settings.

### Q71. How do you test PII masking?
- **Concise:** Parametrised cases for what must and mustn't be masked.
- **Senior:** Tests cover account numbers with spaces or dashes, IBANs and e-mails, and negatives
  like invoice numbers (`INV-2025-0412`), dates and amounts — the first regex version masked the
  invoice number; the test caught it. Integration tests assert the three bank statements' account
  numbers never appear unmasked in extractions or chunks.
- **Follow-up:** Why not use a library like Presidio?
- **Follow-up answer:** It's a good production option for broader entity coverage; regex is
  transparent and dependency-free for the few identifiers here. The masking function is the seam.

### Q72. How do you test the API with auth?
- **Concise:** Configure API keys with roles and assert 401/403/200 per endpoint.
- **Senior:** `tests/e2e/test_auth.py` builds the app with `auth_enabled=true` and keys for each
  role; it checks missing or invalid keys return 401 `unauthenticated`, insufficient role returns
  403, reviewer identity comes from the key, and `/health` stays public.
- **Follow-up:** Why keep `/health` unauthenticated?
- **Follow-up answer:** Load balancers and orchestrators need it; it reveals only status and
  provider names, no data.

## Observability

### Q73. What do you log for each model call?
- **Concise:** Provider, model, prompt version, tokens, latency, cost, success.
- **Senior:** `model_invocation` log and persisted ledger row: operation, provider, model, prompt
  name/version/hash, input/output tokens (flag if estimated), latency, estimated cost, retry
  count, success, error type, `is_mock`, plus request, document and workflow IDs. No prompt text
  or document content is logged.
- **Follow-up:** How do you debug a bad output without logging prompts?
- **Follow-up answer:** Reconstruct: the template is versioned by hash, the inputs (document text,
  question) are stored in the database under access control, and the output is stored on the
  result. Logs stay content-free.

### Q74. How do you correlate events across a request?
- **Concise:** Request, document and workflow IDs in every log line.
- **Senior:** Middleware sets `request_id` in a `contextvar`; the orchestrator sets `document_id`
  and `workflow_id`; the JSON formatter adds them automatically. Audit events also carry
  document and workflow IDs, so logs, audit and metrics line up.
- **Follow-up:** How would that extend to async workers?
- **Follow-up answer:** Propagate IDs in the job payload and restore the contextvars in the
  worker; with OpenTelemetry, propagate trace context so spans join one trace.

### Q75. What metrics would you alert on?
- **Concise:** Error rates, latency, review rate, cost.
- **Senior:** `llm_calls_total{success="false"}` rate, `llm_retries_total`, p95
  `llm_latency_ms` and `workflow_duration_ms`, `workflow_runs_total` by outcome (review and
  failure rates), `guardrail_triggers_total` spikes, cost per hour, and drift status. Alert on
  SLO burn rates rather than raw thresholds.
- **Follow-up:** Is the in-memory metrics store production-ready?
- **Follow-up answer:** No — it's per-process and resets on restart. It's for local visibility;
  production uses the OTel backend with an exporter, or Prometheus scraping each instance.

### Q76. Is OpenTelemetry fully implemented?
- **Concise:** Metrics are emitted through the OTel API; tracing and exporters are not
  configured.
- **Senior:** With `metrics_backend=otel`, counters and histograms go to OTel instruments; without
  a configured `MeterProvider` that's a no-op, which is intentional for local runs. Adding an
  OTLP exporter and tracing spans around workflow steps and provider calls is roadmap work, and
  the README says so.
- **Follow-up:** Where would you put spans first?
- **Follow-up answer:** Around each workflow step and each gateway call (with model, prompt
  version, tokens as attributes) — that's where latency and failures concentrate.

## MLOps

### Q77. How do you version everything that affects model behaviour?
- **Concise:** Prompts, model IDs, schemas, thresholds and evaluation baselines are versioned.
- **Senior:** Prompt files have versions and hashes; model IDs are configuration and recorded on
  every output; schemas and rules are in versioned YAML; thresholds and baselines are in the repo;
  dependency versions are locked. Any output can be traced to the exact prompt, model and code
  version.
- **Follow-up:** What about the data used for evaluation?
- **Follow-up answer:** Synthetic data is generated deterministically by a script and committed
  with its ground truth; real evaluation data would be snapshotted with a content hash.

### Q78. How would you roll out a new model to production?
- **Concise:** Evaluate offline, shadow, canary, then full rollout with monitoring.
- **Senior:** Pass the gate on the offline set with a new baseline; shadow on live traffic
  comparing outputs and review rates; canary a percentage of documents; watch drift (correction
  and review rates, latency, cost); keep instant rollback via configuration.
- **Follow-up:** How do you shadow without doubling cost everywhere?
- **Follow-up answer:** Sample a fraction of traffic, and prioritise document types where the
  old model underperforms.

### Q79. What's the model lifecycle ownership model?
- **Concise:** Clear owners for prompts, models, thresholds and review operations.
- **Senior:** In regulated firms, model-risk management expects documented intended use,
  limitations, validation evidence, monitoring and change control. This repo provides the
  artefacts — ADRs, evaluation reports, drift reports, audit trail — that such a process
  consumes.
- **Follow-up:** Would an LLM prompt change count as a model change?
- **Follow-up answer:** Usually yes — it can materially change behaviour — which is why prompts
  are versioned, hash-locked and gated like code.

## Drift

### Q80. What kinds of drift do you monitor?
- **Concise:** Input distribution, output confidence, human feedback rates and operational
  metrics.
- **Senior:** PSI on document-type mix and confidence distributions; absolute deltas for review,
  rejection, correction, schema-failure, unsupported-answer and refusal rates, and drops in mean
  groundedness and extraction confidence; ratios for p95 latency, tokens and cost per call;
  model and prompt version changes.
- **Follow-up:** Why PSI?
- **Follow-up answer:** It's a standard, interpretable measure in financial model monitoring with
  well-known thresholds (0.1 moderate, 0.25 significant), and it works on binned distributions
  without assumptions.

### Q81. How do you avoid false drift alarms?
- **Concise:** Minimum sample sizes and sensible thresholds.
- **Senior:** Each metric reports `insufficient_data` below `min_samples` (5), and the overall
  status ignores version-info metrics and reports `insufficient_data` when nothing is
  comparable. PSI uses smoothing for empty bins. The demo's real alert (3 of 6 documents
  reviewed vs. the baseline) shows the signal is live.
- **Follow-up:** Is 5 samples enough?
- **Follow-up answer:** It's a demo floor. In production, use hundreds of observations per window,
  or statistical tests with power considered, and compare rolling windows.

### Q82. What do you do when drift is detected?
- **Concise:** Investigate, re-evaluate, adjust prompts, thresholds or models.
- **Senior:** Check whether the input mix changed (new document source), whether a model or
  prompt version changed, and whether human correction rates rose. Re-run evaluation on recent
  reviewed cases; if quality dropped, tighten review routing immediately, then fix the root cause.
- **Follow-up:** Can you auto-remediate?
- **Follow-up answer:** Safe automatic actions exist — lowering auto-approve thresholds to send
  more to review — but changing models or prompts should stay a governed human decision.

## CI/CD

### Q83. What runs in CI?
- **Concise:** Lint, format check, type check, tests, evaluation, quality gate, Docker build and
  health check.
- **Senior:** Five jobs: `quality` (Python 3.12 with Tesseract installed so the OCR test runs;
  install from the lock; ruff; mypy strict; unit/integration/e2e; `run_evals.py`;
  `quality_gate.py`; upload the report), `web` (lint, type check, Vitest, build), `infra`
  (cfn-lint on the CloudFormation templates, deploy script syntax, actionlint on the workflows),
  `e2e` (Playwright against the real API: tour, accessibility, phone layout) and `docker`
  (build, run, poll `/health`). Concurrency groups cancel superseded runs; permissions are
  read-only.
- **Follow-up:** Has this pipeline run on GitHub?
- **Follow-up answer:** Yes, CI passes on GitHub Actions, and the same commands run locally
  through `make check` and `make docker`, so a failure can be reproduced without pushing.

### Q84. Why run the evaluation in CI?
- **Concise:** To catch quality regressions like any other test failure.
- **Senior:** A prompt, rule or retrieval change can silently degrade quality while unit tests
  pass. The gate checks absolute thresholds and regression against the committed baseline; since
  mock mode is deterministic, any change is a real code or prompt effect, not noise.
- **Follow-up:** How would this work with real providers?
- **Follow-up answer:** A separate, scheduled or release-candidate job with credentials, a
  per-provider baseline, and tolerance for run-to-run variance.

### Q85. How does CD work here, and what would production CD add?
- **Concise:** After CI passes on `main`, an approved GitHub Actions job deploys with short-lived
  AWS credentials from OIDC and runs the live smoke tests.
- **Senior:** `deploy.yml` triggers on a successful `ci` run for `main`, waits in the GitHub
  environment `production` for a reviewer, then assumes `docintel-github-deploy` through GitHub's
  OIDC token (no stored AWS keys; the trust policy pins the repository and the environment). That
  role can only create change sets on the demo stack that name the CloudFormation service role,
  which holds the resource permissions. It builds the ARM64 image natively, deploys, and runs
  `make smoke-live`. Honest status: the AWS roles exist and the workflow passes actionlint, but it
  hasn't run yet because the GitHub environment hasn't been created; deploys so far were by hand
  with `make deploy`. Production CD would add a staging environment with a real-provider
  evaluation, image signing with an SBOM and vulnerability scan, blue/green or canary rollout,
  and config (model IDs, thresholds) promoted as versioned artefacts.
- **Follow-up:** How do you roll back a bad prompt quickly?
- **Follow-up answer:** Prompts ship with the image, so roll back the image; or keep prompt
  selection in config to switch versions without a rebuild.

## Security & privacy

### Q86. How are secrets managed?
- **Concise:** Environment variables only; nothing committed.
- **Senior:** `pydantic-settings` reads `DOCINTEL_*` variables; secrets are `SecretStr`; `.env`
  is git-ignored and `.dockerignore`d; AWS uses the credential chain (roles), so there are no
  AWS keys in config. Logs redact credential-like keys. Production: a secrets manager injecting
  env vars at runtime.
- **Follow-up:** Found a bug there, didn't you?
- **Follow-up answer:** Yes — the redaction pattern matched "token" inside `input_tokens`, so
  token counts were logged as `[REDACTED]`. It was over-redaction (safe but useless), found by
  reading container logs, fixed with a precise pattern and covered by tests.

### Q87. How does authentication and authorisation work?
- **Concise:** Optional API keys mapped to roles; endpoints require minimum roles.
- **Senior:** `X-API-Key` compared with `hmac.compare_digest`; roles viewer < analyst < reviewer
  < admin; e.g. upload/process need analyst, review actions need reviewer, evaluation runs and
  audit verification need admin. Enabling auth without keys fails at start-up. Local mode is
  unauthenticated and documented as such.
- **Follow-up:** What's wrong with API keys for production?
- **Follow-up answer:** No user identity, rotation is manual, and keys leak. Use OIDC with
  short-lived tokens and map groups to roles.

### Q88. What data leaves your environment when using Bedrock or Azure?
- **Concise:** The document text and questions sent in prompts.
- **Senior:** The full extracted text goes to the provider for classification and extraction,
  and retrieved chunks for Q&A. ADR-009 states this plainly. Controls: region pinning, provider
  data-processing terms (no training on prompts), private networking, and — if required —
  redacting identifiers before model calls, at a cost to extraction.
- **Follow-up:** Why not mask account numbers before sending to the model?
- **Follow-up answer:** The bank-statement schema needs the account number (it's masked in the
  result); masking before the call would make the model unable to extract it. It's a policy
  trade-off per field.

### Q89. How do you protect the audit trail from tampering?
- **Concise:** Hash chaining: each event includes the previous event's hash.
- **Senior:** `event_hash = sha256(prev_hash + canonical(event))`; `/audit/verify` recomputes
  the chain and returns the first broken sequence. Tests modify a stored event and assert
  detection. This detects tampering; it doesn't prevent a DB admin rewriting the whole chain.
- **Follow-up:** How would you make it tamper-evident against privileged users?
- **Follow-up answer:** Periodically anchor the head hash in a write-once store (S3 Object Lock,
  QLDB-style ledger) or sign checkpoints with a KMS key the DB admins can't use.

### Q90. What upload attacks do you consider?
- **Concise:** Oversized files, non-PDFs, malicious PDFs and path traversal.
- **Senior:** Size capped while reading; magic bytes and parse validation; generated storage
  names (no user path components); atomic writes; encrypted PDFs flagged; active-content markers
  (`/JavaScript`, `/Launch`, `/EmbeddedFile`) flagged via a byte scan; pypdf in a process that
  never executes content. Not implemented: malware scanning and sandboxed parsing.
- **Follow-up:** Is the active-content scan reliable?
- **Follow-up answer:** It's a heuristic — compressed object streams can hide markers. It's a
  signal, not a guarantee; production should use AV scanning and a sandboxed parser.

### Q91. Do you claim any compliance certifications?
- **Concise:** No.
- **Senior:** The project implements controls that support compliance programmes — audit
  trails, access control, PII-aware logging — but certifications like SOC 2 or PCI DSS apply to
  organisations and operated systems, not to a codebase. The README and ADR-009 list what is
  and isn't implemented.
- **Follow-up:** What would PCI DSS scope imply if card numbers appear in documents?
- **Follow-up answer:** Storing PANs brings the system into cardholder-data scope; you'd need to
  detect and truncate PANs before storage and indexing, or keep such documents out of the
  platform.

## Distributed systems

### Q92. How would you make processing asynchronous?
- **Concise:** Enqueue a job on upload/process; workers pick it up; clients poll or get webhooks.
- **Senior:** `POST /process` returns 202 with a workflow ID; a queue (SQS) carries the job;
  workers run the same orchestrator; the state machine already persists status, so polling
  `GET /documents/{id}` works. Idempotency via workflow IDs, visibility timeouts, and a
  dead-letter queue for poison messages.
- **Follow-up:** What happens if a worker crashes mid-workflow?
- **Follow-up answer:** The message becomes visible again; the worker sees the document in an
  in-progress state and restarts from `INGESTED` (steps are idempotent: chunk IDs are content
  hashes, extraction creates a new version). A durable workflow engine would resume per step.

### Q93. What consistency issues exist between DB, file store and vector store?
- **Concise:** No distributed transaction; partial failures can leave them out of sync.
- **Senior:** Writes happen in order (file, then DB record; index, then state transition), and
  failures move the workflow to `FAILED` for retry. Idempotent upserts make retries safe. At
  scale, use an outbox table to drive indexing and a reconciliation job.
- **Follow-up:** Can a document be `READY` without chunks?
- **Follow-up answer:** Not through the normal path — `INDEXED` must precede `READY`. A later
  index loss would need reconciliation; `/health` checks vector store availability, not
  completeness.

### Q94. How do you handle idempotency on uploads?
- **Concise:** De-duplicate by content hash.
- **Senior:** SHA-256 of the bytes; re-uploading the same file returns the existing document with
  `duplicate: true` rather than creating a copy. In a distributed setup, a unique constraint on
  the hash handles races.
- **Follow-up:** What if the same content should be processed twice?
- **Follow-up answer:** Use reprocess on the existing document (a new workflow run), which keeps
  history instead of duplicating documents.

### Q95. How would you rate-limit model calls across workers?
- **Concise:** A shared token bucket or queue concurrency limits.
- **Senior:** Provider quotas are account-wide, so per-process limits are insufficient. Use a
  distributed limiter (Redis) or cap worker concurrency to the quota, with backoff on throttling
  and priority lanes for interactive Q&A over batch processing.
- **Follow-up:** Where does the gateway fit?
- **Follow-up answer:** It's the single choke point, so a limiter plugs in there without touching
  business code.

## Financial services

### Q96. What makes financial document AI different from generic document AI?
- **Concise:** Higher accuracy bar, auditability, regulation and adversarial risk.
- **Senior:** Numbers must be exact, provenance must be shown, decisions must be reviewable
  years later, data is sensitive, and documents can be adversarial (fraudulent invoices,
  injected payment instructions). That's why validation rules, evidence verification, audit
  chains and human control are core features, not add-ons.
- **Follow-up:** Give an example of a domain rule you implemented.
- **Follow-up answer:** Bank statement reconciliation: opening balance + credits − debits must
  equal the closing balance within tolerance; a failure routes to review.

### Q97. How does this fit model-risk management expectations?
- **Concise:** It provides documentation, validation evidence, monitoring and controls.
- **Senior:** Model inventory data (model, prompt versions), intended use and limitations
  (README, ADRs), validation (evaluation reports, gate), ongoing monitoring (drift, review
  rates), and change control (hash-locked prompts, baselines). Model-risk frameworks expect these
  artefacts; the organisation's process applies them.
- **Follow-up:** What would a validator challenge first?
- **Follow-up answer:** The evaluation data's representativeness — synthetic data isn't
  sufficient evidence of real-world performance.

### Q98. How would you use this for accounts-payable invoice processing?
- **Concise:** Extract invoice fields, validate, match to purchase orders, route exceptions.
- **Senior:** Current capabilities cover extraction, arithmetic validation and injection
  detection (e.g. changed bank details in an invoice). Production AP adds vendor-master
  validation, PO/receipt matching, duplicate-invoice detection across vendors, and payment
  controls — all deterministic steps around the AI.
- **Follow-up:** How would you catch invoice fraud like changed bank details?
- **Follow-up answer:** Compare extracted remittance details with the vendor master and require
  out-of-band verification on mismatch; never let a document alone change payment details.

### Q99. What retention considerations apply?
- **Concise:** Keep records as long as regulation requires, delete when no longer needed.
- **Senior:** Retention periods vary by jurisdiction and record type; audit events may need longer
  retention than documents. Deletion must cover file store, database, vector index and backups.
  The platform supports deletion internally but doesn't expose retention policies yet — documented
  as not implemented.
- **Follow-up:** How do you reconcile an append-only audit trail with deletion rights?
- **Follow-up answer:** Keep audit events free of personal content (IDs, hashes, reasons —
  as here), so documents can be deleted while the audit history remains intact.

## Architecture

### Q100. Why a modular monolith and not microservices?
- **Concise:** Simpler to build, test and operate at this scale; seams allow a later split.
- **Senior:** Microservices add network failure modes, distributed tracing needs and deployment
  overhead before there's a scaling reason. The natural split points — API, processing workers,
  retrieval — are already separated by interfaces and the container.
- **Follow-up:** What would you split first?
- **Follow-up answer:** Processing into queue-driven workers, because its resource profile (CPU
  for OCR, long model calls) differs most from the API's.

### Q101. What's the role of the ModelGateway?
- **Concise:** The single path to any LLM, applying cross-cutting concerns uniformly.
- **Senior:** It renders versioned prompts, enforces timeouts and retries, extracts and validates
  JSON with a repair attempt, estimates cost, records every invocation, emits metrics and logs,
  and maps failures to typed errors. Business services never touch providers directly, which
  makes provider swaps, testing and auditing straightforward.
- **Follow-up:** Isn't that a god object?
- **Follow-up answer:** It has one responsibility — safe model invocation — and delegates
  prompts, retries, pricing and persistence to collaborators. Business logic stays out of it.

### Q102. How did you document architectural decisions?
- **Concise:** Ten ADRs in `docs/adr/`.
- **Senior:** Orchestration framework, vector store, provider abstraction, deterministic
  workflow, RAG architecture (including the chunk-size sweep), evaluation methodology, HITL
  strategy, observability and sensitive data. Each records context, decision, alternatives,
  consequences and when to revisit.
- **Follow-up:** Which decision are you least sure about?
- **Follow-up answer:** Synchronous processing — right for the demo, wrong under load; it's the
  first thing I'd change.

### Q103. How is configuration structured?
- **Concise:** Typed settings from environment variables, plus YAML for domain configuration.
- **Senior:** `Settings` (pydantic-settings) for runtime and provider config with cross-field
  validation (overlap < chunk size, strong score > min score, auth requires keys). YAML for
  document types, drift thresholds and pricing — domain data that non-engineers can review.
- **Follow-up:** Why validate config at start-up?
- **Follow-up answer:** Fail fast with a clear message instead of failing on the first request
  in production.

## Scalability

### Q104. Where are the bottlenecks today?
- **Concise:** Synchronous processing, SQLite and embedded Chroma.
- **Senior:** Processing ties up a request thread for seconds (longer with OCR or real models);
  SQLite serialises writes; embedded Chroma is single-node; in-memory metrics are per-process.
  Each has a known replacement: workers, Postgres, managed vector store, OTel exporter.
- **Follow-up:** Rough throughput estimate with real models?
- **Follow-up answer:** Dominated by LLM latency: two calls per document (classify + extract) at
  a few seconds each; throughput scales with worker concurrency up to provider quotas.

### Q105. How would you scale retrieval to millions of chunks?
- **Concise:** Managed vector store with ANN indexes and metadata filters.
- **Senior:** HNSW-based indexes in OpenSearch or pgvector, partitioning by tenant, filter-first
  queries, caching of frequent question embeddings, and asynchronous indexing. Per-document
  questions stay cheap because of the document filter.
- **Follow-up:** What about re-indexing cost on an embedding change?
- **Follow-up answer:** Batch re-embedding in the background into a new index, dual-read during
  cut-over, and throttled to provider quotas.

### Q106. How do you control cost at scale?
- **Concise:** Track tokens and cost per call, cache, and right-size models.
- **Senior:** The ledger gives cost per operation and model; classification results can be cached
  by content hash (duplicates are already de-duplicated at upload); simpler steps can use smaller
  models; the drift monitor alerts on tokens-per-call and cost-per-call ratios.
- **Follow-up:** Where's the biggest saving?
- **Follow-up answer:** Usually extraction prompt size — sending only relevant pages, and using a
  smaller model for classification.

## Troubleshooting

### Q107. A user says an answer is wrong. How do you investigate?
- **Concise:** Look at citations, retrieval scores, groundedness and the stored invocation.
- **Senior:** The answer record has citations, retrieval scores, groundedness, model and prompt
  version; the audit trail has the event; the invocation ledger has latency and tokens; logs with
  the request ID show the flow. Then classify the failure: retrieval miss, model misread, or bad
  source data — and add the case to the evaluation set.
- **Follow-up:** And if groundedness was 1.0 but the answer is still wrong?
- **Follow-up answer:** Likely misattribution — a number from the wrong row or period that exists
  in the evidence. Fix with better chunking or prompts, and add a regression case.

### Q108. Review rate suddenly doubled. What do you check?
- **Concise:** Which review reasons increased, and whether inputs or versions changed.
- **Senior:** Break down `reviews_created_total` by reason; check the drift report for
  document-type PSI and version changes; look for a new document source (e.g. scans → `ocr_used`),
  a provider degradation (`retries_exhausted`), or a prompt change lowering confidence.
- **Follow-up:** What if it's `retries_exhausted`?
- **Follow-up answer:** Provider throttling or an outage: check error types in the invocation
  ledger, provider status, and quota; temporarily reduce concurrency.

### Q109. Extraction returns nulls for a field that is clearly on the page. Why?
- **Concise:** The label differs from expectations, OCR misread it, or evidence verification
  failed.
- **Senior:** Check the extracted text (native vs OCR), the field description in
  `app/extraction/schemas.py` (and, in mock mode, the label synonyms in
  `config/document_types.yaml`), the raw model output in the review case, and validation messages
  (a value that failed coercion is recorded as invalid, not silently dropped).
- **Follow-up:** How do you prevent recurrence?
- **Follow-up answer:** Add the layout to the evaluation set, update synonyms or the prompt with a
  version bump, and confirm the gate passes.

### Q110. The service returns 503 on processing. What's happening?
- **Concise:** Likely a vector-store error.
- **Senior:** `VectorStoreError` maps to 503 and moves the workflow to `FAILED`; `/health` shows
  `checks.vector_store=false` if the store is unavailable. Check disk and permissions on the data
  volume (the container has a read-only root filesystem, so only `/data` and `/tmp` are writable).
- **Follow-up:** How does the document recover?
- **Follow-up answer:** Once the store is healthy, re-run processing: `FAILED → INGESTED` is an
  allowed transition, and indexing is idempotent.

### Q111. Audit verification fails. What does it mean?
- **Concise:** An event was modified, deleted or inserted outside the service.
- **Senior:** `/audit/verify` returns the first broken sequence number; everything after it is
  unverified. Treat it as a security incident: preserve the database, compare with backups, and
  review DB access logs.
- **Follow-up:** Could a bug cause it?
- **Follow-up answer:** A serialisation change to audit events would break recomputation, which
  is why the hash covers a canonical JSON form and there's a test for it; schema changes to
  events need a versioned hash scheme.

### Q112. Tests pass locally but fail in CI. Common causes here?
- **Concise:** Environment differences — Tesseract, dependency versions, file paths.
- **Senior:** CI installs Tesseract, so the OCR test runs there but is skipped locally without
  it; CI installs from the lock while a local environment may have drifted; tests use `tmp_path`
  and `_env_file=None` so a local `.env` can't leak in.
- **Follow-up:** How did you prevent `.env` from affecting tests?
- **Follow-up answer:** Test settings are built with `Settings(_env_file=None, …)` via
  `tests/support.make_settings`, so tests are hermetic regardless of the developer's environment.

## Fine-tuning

### Q113. Did you fine-tune a model? How did you set it up?
- **Concise:** I prepared an Azure OpenAI fine-tuning experiment for extraction: a seeded
  synthetic corpus, training records in the exact production prompt format, a cost-guarded job
  script and an evaluation harness. The training job itself hasn't run yet.
- **Senior:** 320 synthetic documents across five types, with layouts, label wording, number
  formats, missing fields, distractors and planted instructions varied. Splits are by layout
  family and by name pool (four families train, one validation, two test per type), so the test
  set has layouts and names the model never saw, and tests check that nothing crosses. Each
  record is the production prompt (`extraction.financial_entities@1.2.0`, hash pinned) over text
  read back by the production PDF extractor, and each target is replayed through the real
  `EntityExtractor`; it's kept only if every value comes back with verified evidence. The job
  script estimates cost offline (about 712,000 billed tokens, roughly $1.07 for gpt-4.1-nano at
  the listed prices) and refuses to submit above a cap or without an explicit cost confirmation.
- **Follow-up:** Why synthetic data, and what does that limit?
- **Follow-up answer:** There's no real customer data in this project, and synthetic data comes
  with exact labels. The cost is realism: a model that wins here has learnt these generators, not
  real statements. The experiment shows the method; real reviewer-corrected documents would be the
  production training set (fine-tuning pathway document).

### Q114. How will you judge whether fine-tuning was worth it?
- **Concise:** Same held-out documents, same extractor, same prompt: base nano, fine-tuned nano
  and base mini side by side on accuracy, invented values, JSON validity, latency and cost.
- **Senior:** The baseline is already measured: base gpt-4.1-mini scored 0.984 field accuracy on
  the 80 held-out documents and 0.989 on the 25 original samples, at about $0.001 a document.
  Its errors were planted "report the fee as X" instructions (followed in two of the three
  injected documents across runs) and reporting 0.0 for "Tax: exempt" where the labels say null.
  Every wrong value was flagged by production validation. The fine-tuned model is worth it only
  if it matches mini's accuracy at nano's cost, or fixes those failure types, without new ones;
  the result is recorded either way.
- **Follow-up:** Could fine-tuning make injection worse?
- **Follow-up answer:** It could if the training data taught the model to copy instructions from
  documents. Here the targets always ignore the planted note, the held-out set has its own
  planted notes, and the guardrails and evidence checks stay in place whatever the model does.
